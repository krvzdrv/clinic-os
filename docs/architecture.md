# Архитектура клинической ИС для маленькой клиники

## Постановка задачи

Маленькая клиника, врач-эксперт по контролю качества. Нужно, чтобы при работе врача
с конкретным пациентом информационная система:
- подсказывала правильные действия по протоколу (CDS);
- учитывала все релевантные факторы (тяжесть, ко-морбидности, аллергию, противопоказания);
- считала метрики качества для руководства;
- была доступна, поддерживаема и бесплатна.

## Принцип: разумная архитектура, а не «как у больших»

Сравнение с ERP в парикмахерской — правильная аналогия. Kaiser Permanente и Intermountain
Healthcare реализовали guideline-driven CDS, но у них команды из сотен людей и бюджеты
в миллионы. Маленькая клиника без IT-команды не может повторить это.

Поэтому: **сохраняем архитектурные принципы, упрощаем реализацию.**

## Слои архитектуры

```
┌──────────────────────────────────────────────┐
│  Слой 6: Метрики качества (дашборд)          │  ← для руководства
├──────────────────────────────────────────────┤
│  Слой 5: CDS Hooks (точка оказания помощи)   │  ← подсказки врачу
├──────────────────────────────────────────────┤
│  Слой 4: Путь пациента (state machine)       │  ← где пациент в протоколе
├──────────────────────────────────────────────┤
│  Слой 3: Движок правил (CQL-like)            │  ← single source of truth
├──────────────────────────────────────────────┤
│  Слой 2: Терминологии (МКБ, LOINC, ATC)      │  ← коды диагнозов, измерений, лекарств
├──────────────────────────────────────────────┤
│  Слой 1: FHIR-модель данных                  │  ← Patient, Condition, Observation
├──────────────────────────────────────────────┤
│  Слой 0: Хранилище                           │  ← Supabase Postgres / SQLite
└──────────────────────────────────────────────┘
```

**Сервис подключения к БД (`db.py`).** Между репозиторием (`fhir_store`) и
самой базой стоит тонкий сервис `db.py` — единственный модуль, работающий
с драйвером БД. Он даёт единый интерфейс `fetchone / fetchall / execute` с
плейсхолдерами `%s` и переключает хранилище одной переменной `DATABASE_URL`:
задана → Postgres на Supabase, не задана → локальный SQLite. Остальные слои
о переключении ничего не знают.

### Single source of truth — ключевой принцип

Одни и те же правила используются и для подсказок врачу (Слой 5),
и для метрик качества (Слой 6). Функция `protocol_cap.evaluate_cap()` в
`protocol_cap.py` вызывается:
- из `cds_service.cds_patient_view()` → карточки-подсказки в карте пациента;
- из `rules_engine.quality_measure_cap()` → цифра на дашборде.

Один код — два применения. Это исключает расхождение между «что видит врач»
и «что считает отчёт».

## Реализация (MVP)

| Слой | В «учебнике» | У нас (MVP) | Файл |
|---|---|---|---|
| Подключение | — | сервис БД (Postgres/SQLite) | `db.py` |
| 0 — Хранилище | HAPI FHIR + PostgreSQL | Supabase Postgres / SQLite | `schema.sql` + `fhir_store.py` |
| 1 — Модель | FHIR R4 resources | FHIR-подобные таблицы | `fhir_store.py` |
| 2 — Терминологии | SNOMED CT, LOINC server | коды в полях (J18.9, LOINC, J01CA04) | встроено |
| 3 — Правила | CQL Engine (cql-execution) | Python-функции | `rules_engine.py` |
| 3b — Регламент | CPG-on-FHIR (PlanDefinition) | независимый валидатор | `protocol_cap.py` (ВП, КП МЗ РБ №768) |
| 4 — Путь пациента | CPG-on-FHIR (PlanDefinition) | state machine в таблице | `fhir_store.py`, `care_plan_service.py` |
| 5 — CDS | CDS Hooks микросервис | функции в Flask | `cds_service.py` |
| 6 — Метрики | Measure + CQL population | Python-агрегация | `rules_engine.py` |
| UI | SMART on FHIR + React | Flask-шаблоны (HTML/CSS) | `templates/` |

## Чем пожертвовали (осознанно)

- **CQL Engine** → Python-функции. CQL — мощный язык, но требует Java, отдельный
  сервис, экспертизу. Python-функции читаются как текст и поддерживаются одним человеком.
  Миграция на CQL возможна позже без изменения бизнес-логики.
- **HAPI FHIR** → SQLite. HAPI FHIR — Java + PostgreSQL + поддержка. SQLite — один файл,
  переносится на любой компьютер, бэкап = копия. Модель данных FHIR-подобная, поэтому
  миграция на настоящий FHIR-сервер возможна без переписывания правил.
- **CPG-on-FHIR** → state machine в таблице. CPG-on-FHIR — академический стандарт,
  ещё зреющий. Внутренняя state machine pathway (без диагноза → лечение →
  стационар/ОРИТ → выздоровление / смена терапии) — не показывать врачу как
  «этапы протокола»; якорь UI — диагноз МКБ и CDS.
- **Микросервисы** → монолит. Один Flask-процесс, один URL, ноль сложности.
  Для 5–10 врачей и 1000 пациентов — более чем достаточно.
- **Camunda/BPMN** → не используется. BPMN — для организационных процессов
  (согласования, SLA, эскалации). У маленькой клиники этого нет. State machine
  пациента реализована в коде. Camunda встаёт позже без переписывания правил.

## Что не пожертвовали (принципы сохранены)

- **Single source of truth** — одни правила для подсказок и метрик.
- **FHIR-подобная модель** — миграция на настоящий FHIR без боли.
- **CDS Hooks концепция** — карточки в момент работы врача (info / suggestion / hard-stop).
  Политика сигналов (continuous eval + осознанный override + эпизод не «зелёный»):
  [`docs/processes/CDS_SIGNALING.md`](./processes/CDS_SIGNALING.md) / `process_registry.yaml` → `cds_policy`.
- **Слои** — данные, правила, сервис, UI разделены, даже если в одном процессе.
- **Alert fatigue управление** — мало карточек, только релевантные.

## Профили протоколов (Слой 3b)

Регламент — независимый валидатор, который проверяет **совокупность** ресурсов
пациента (диагноз + измерения + препараты + цель) на соответствие клиническому
протоколу. В отличие от CDS (Слой 5), который подсказывает в момент одного
действия, регламент отвечает на вопрос «вся картина по пациенту соответствует
протоколу?».

Каждый профиль — отдельный модуль, чтобы правила одного заболевания не смешивались
с другим. Главный вход каждого профиля — `evaluate_<profile>(pid) → {applicable,
compliant, gaps[]}`.

| Профиль | Протокол | Файл | Что проверяет |
|---|---|---|---|
| Внебольничная пневмония (взрослые) | КП МЗ РБ №768 от 05.07.2012 | `protocol_cap.py` | амбулаторный и стационарный блоки, тяжесть по SpO2/ДН, показания к госпитализации и ОРИТ, обязательные исследования (ОАК, СРБ, пульсоксиметрия, R-графия), выбор АБТ (амоксициллин/амокс-клавуланат/макролид; в стационаре — цефтриаксон, карбапенемы, линезолид) с учётом факторов резистентности, аллергии на β-лактамы, MRSA, аспирации, гриппа, симптоматическая терапия, оценка эффективности АБТ через 48–72 ч, step-down в/в→per os, длительность курса, критерии выписки, повторная R-графия |

Профиль ВП проверен сквозным сценарием на облачной БД (Supabase): обращение →
выявление аллергии → контроль через 72 ч (нет эффекта) → смена АБТ и выздоровление,
а также тяжёлый случай (SpO2 < 90 → госпитализация, показана R-графия).

| CDS | функция в Flask | отдельный CDS Hooks микросервис |

| Процессы | код | Camunda (если появятся согласования) |

Каждый шаг — постепенный, без переписывания предыдущих слоёв.

## Про Camunda — почему не сейчас

BPMN/Camunda — слой **организационных процессов**: «пациент записался →
врач принял → назначение выписано → счёт». Вопрос: кто, что, в каком
порядке, с какими сроками.

CQL/CDS — слой **клинической логики**: «если SpO2 < 90 → показана госпитализация».
Вопрос: что medically правильно для конкретного пациента.

Они работают вместе: Camunda ведёт процесс, на шаге «назначение» вызывает
CDS-сервис (который исполняет CQL) — и получает hard-stop или suggestion.

Для маленькой клиники Camunda избыточен. State machine пациента (6 этапов)
проще в коде. Camunda имеет смысл когда:
- много участников и согласований (зав. отделением → главврач → страховая);
- жёсткие SLA с эскалацией;
- нужно визуально рисовать процессы, чтобы менять без программиста.

## Реальные примеры «хорошо реализовано»

- **Intermountain Healthcare (Юта)** — пионеры, Clement McDonald, с 1970-х.
- **Kaiser Permanente** — HealthConnect на базе Epic, ~12 млн пациентов.
- **Mayo Clinic, Cleveland Clinic** — академические гиганты.
- **NHS (Великобритания)** — национальные протоколы NICE, частично оцифрованы.
- **Дания** — одна из самых цифровых систем здравоохранения.

Для маленькой клиники — практически нигде не реализовано хорошо.
Эти технологии требуют команд и бюджетов. Наш подход — разумный минимум,
который даёт измеримый эффект и поддерживается одним человеком.
