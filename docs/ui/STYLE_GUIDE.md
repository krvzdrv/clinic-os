# Style guide — clinic-os (для агентов)

Reference: прикладывай к задаче на UI вместе с  
[`ui-design-guide.md`](./ui-design-guide.md) (компоненты) и [`CLINICAL_HIERARCHY.md`](./CLINICAL_HIERARCHY.md) (иерархия).  
Cursor: `.cursor/rules/clinic-ui-patterns.mdc`. Токены: `static/clinic.css`.

---

## 0) Что переносится, а что нет

| | |
|--|--|
| **Не копировать буквально** | Токены чужих чат-виджетов (`--surface-1` из чужой системы) с *их* hex. У нас свои значения. |
| **Переносится** | Архитектура: CSS custom properties, роли (success/danger/warning), пары фон+текст, labeled rows, Tabler Icons, connector rail. |

Агент пишет код **под токены clinic-os**. Семантические имена (`--text-danger`) — алиасы на наш канон; они уже объявлены в `clinic.css`.

## 1) Канон токенов (graphite ward)

Палитра: тёплый камень + угольные кнопки + приглушённый steel.  
**Не:** teal-SaaS, terracotta/cream-marketing, кислотный blue-500, purple glow, dark-mode «AI SaaS».

### Поверхности и текст

| Роль | Канон | Семантический алиас |
|------|-------|---------------------|
| Фон страницы | `--cream` | `--surface-0` |
| Карточка / белая плоскость | `--surface` | `--surface-1` |
| Приглушённая панель | `--tint` | `--surface-2` |
| Текст основной | `--ink` | `--text-primary` |
| Текст вторичный | `--soft` | `--text-secondary` |
| Текст тусклый / лейблы | `--faint` | `--text-muted` |
| Граница | `--line` | `--border`, `--border-strong` |

### Семантические пары (всегда вместе)

| Роль | Фон | Текст | Линия |
|------|-----|-------|-------|
| success | `--green-bg` / `--bg-success` | `--green` / `--text-success` | `--green-line` / `--border-success` |
| danger | `--red-bg` / `--bg-danger` | `--red` / `--text-danger` | `--red-line` / `--border-danger` |
| warning | `--bg-warning` | `--text-warning` | `--border-warning` |
| neutral | `--tint` | `--faint` | `--line` |

**Правило:** никогда не мешать роли (`background: var(--bg-danger); color: var(--text-success)` — запрещено).  
Никогда чёрный/ink на цветном фоне бейджа — только парный `--text-{role}`.

### Действие и типографика

| | |
|--|--|
| Кнопка primary | `--accent` / `--accent-hover` (graphite-navy) |
| Шрифт | `--font` → IBM Plex Sans |
| Радиус | `--radius` → 8px (бейджи в иерархии — 6px) |

Новые hex в шаблонах **не вводить**. Нужен новый смысл — сначала алиас в `:root`, потом использование.

## 2) Иконки

- Набор: [Tabler Icons](https://tabler-icons.io/) (outline), webfont `ti ti-*`.
- В карточке пациента уже подключён CDN (см. `templates/patient.html`).
- Иконка в **лейбле** атрибута (~13px, цвет `--text-muted`), не в значении.
- По смыслу: `ti-stethoscope` диагноз · `ti-pill` лечение · `ti-target-arrow` цель · `ti-calendar` даты · `ti-flask` лаб.

## 3) Компонентные паттерны (кратко)

Полный промпт: [`CLINICAL_HIERARCHY.md`](./CLINICAL_HIERARCHY.md).

1. **Nested hierarchy + connector rail** — диагноз-контейнер; дети с `border-left: 2px solid var(--border)`; визит снаружи.
2. **Labeled attribute row** — лейбл 12px muted + иконка; значение 14px; статус — pill справа (`justify-content: space-between`), не в тексте.
3. **Issue внутри родителя** — DetectedIssue / несоответствие протоколу внутри диагноза; акцент `border: 2px solid var(--border-danger)`.
4. **Бейджи** — классы `.badge.green|red|grey` или явные `background: var(--bg-*); color: var(--text-*)`.

**Запрещено:** левая цветная полоса на всю карточку (accent bar). Connector rail — только у списка детей.

## 4.5) Текст значений (`.attr-value`, none-плейсхолдеры)

Значение атрибута — **фрагмент данных**, не предложение. Правило (уже де-факто
соблюдалось в «Лечение» / «Общее состояние», но не было записано — отсюда
разъезд с текстом цели терапии):

| | Правило | Пример |
|--|---------|--------|
| Регистр | Как естественно пишется термин: имя препарата/диагноза — с большой (собственное имя); прилагательное-состояние — со строчной | `Амоксициллин`; `удовлетворительное`; `нет активной АБТ` |
| Точка в конце | **Никогда** — это фрагмент, не предложение | `до 2026-08-01` (не `до 2026-08-01.`) |
| Несколько фактов в одном значении | Разделять « · » (middot), не запятой — запятая читается как список внутри предложения, middot — как соседние поля одной карточки | `500 мг · 3 раза в день · внутрь` |
| Несколько отдельных записей в списке | Разделять `; ` | несколько активных препаратов |
| Пусто/нет данных | `<span class="none">` — строчная, если это продолжение значения того же атрибута (`нет активной АБТ`); с большой, если это самостоятельное сообщение о пустом разделе (`Нет заказов и результатов`, `Записей пока нет`) |

Не переносить сюда стиль баннеров/вердикта (`headline`, «Показан перевод в ОРИТ») — там предложение, у него свои правила (капитализация, без точки в конце, язык врача). Правило этого раздела — только для `.attr-value` внутри карточки диагноза/визита.

## 4.6) Слэш «X/Y» в клиническом тексте — не как связка слов

`/` без пробелов между двумя клиническими терминами читается неоднозначно (И? ИЛИ?
синоним?) и на практике расползается по написанию: один и тот же критерий получал
разный текст в разных списках причин («двусторонняя/многодолевая» в одном месте,
«двустороннее/многоочаговое» — в другом; тот же флаг). Правило:

| Ситуация | Как писать | Пример |
|--|---------|--------|
| Альтернативные признаки одного критерия (это ИЛИ то) | Слово **«или»**, не `/` | `двустороннее или многоочаговое поражение лёгких` |
| Список из 2–3 отдельных обстоятельств в скобках-уточнении | **`, `** или **«или»** перед последним | `(мальабсорбция, заболевание ЖКТ или непереносимость)` |
| Короткая доменная аббревиатура (уже устоявшаяся во всём коде) | `/` **без** пробелов — не трогать | `в/в`, `в/м`, `р/сут`, `мг/кг` |
| Два кода/сокращения одной природы рядом (не слово-термин) | `/` **с** пробелами | `ОАМ / ЭКГ` |

Текст критерия по клиническому флагу (`has_clinical_flag`) — **всегда** через
`terminology.CLINICAL_FLAGS[код][0]` (helper `rules_engine.flag_criterion_text`),
а не новая строка в каждом списке причин — иначе один флаг снова получит два текста.

Проверяется автоматически: `tools/style_gate.py` (пункт 5).

## 4.7) Списки, которые растут годами — активное карточкой, история свёрнутым списком

У пациента, которого ведут долго (хронические/повторные диагнозы, много приёмов),
любой список «одна карточка на запись» без деления на активное/прошлое рано или
поздно превращается в стену одинаковых крупных блоков — 20 диагнозов за 10 лет
выглядят так же тяжело, как 20 приёмов. Правило (единое для всех таких списков):

| Что | Активное / текущее | История |
|--|--|--|
| Диагнозы (`#conditions-list`) | Полная `.dx-card` — лечение, цель терапии, CDS-подсказка | Свёрнутый `history-fold` → компактная `.visit-row` (дата · название+код · статус), клик — переход к приёму, где поставлен |
| Приёмы (`#panel-encounters`) | Текущий приём — полная `.enc-card` | `history-fold` со списком `.visit-row`, пагинация «Показать ещё» |

Признак, что список нужно делить так же: у сущности есть явный статус
активна/закрыта (`clinical_status`, `status`) **и** количество записей растёт с
каждым годом наблюдения, а не ограничено одним эпизодом. Показывать полной
карточкой — только то, что сейчас требует решения врача; закрытое/разрешённое —
одной строкой в свёрнутом блоке, не карточкой.

Данные, привязанные к конкретной записи (цель терапии → диагноз через
`care_plan.condition_id`, CDS-вердикт → диагноз через `verdict_by_condition`),
всегда фильтровать по id этой записи, а не показывать список пациента целиком под
каждой карточкой — иначе цель прошлого эпизода всплывает под новым диагнозом того
же кода.
