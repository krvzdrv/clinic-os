# BPMN Practices — практики моделирования для clinic-os

Канон рисования BPMN. Структура верхнего уровня — как в Alumineu: **фазы = подпроцессы**.

## 0. Главный принцип: ведение ≠ протокол ≠ инструкция UI

| Слой | Что это | Где живёт |
|------|---------|-----------|
| **Ведение пациента** | Как движется лечение: визит и отдельно контроль | Главные BPMN: `care-outpatient-mature.bpmn` + `care-outpatient-control-mature.bpmn` |
| **Протокол** | Сверка сделанного с правилами по **активным диагнозам** (их может быть несколько) | Аннотация на шагах «назначить» / «контроль» + движок в приложении; **не** отдельная дорога на каждый КП |
| **Инструкция UI** | Какие поля заполнить | Экран, не BPMN |

**Главный рассказ врачам — общий путь ведения** со всеми типичными ветками (госпитализация, направление, дообследование, наблюдение без назначения, нет эффекта, ухудшение, закрытие заболевания).  
Не рисовать «процесс только для пневмонии» как основной путь клиники.

**Жёстко:** в процессах ведения (`care_*`) **нет** конкретных диагнозов в `name` (ни пневмонии, ни анемии, ни МКБ). Диагноз на схеме — «Диагноз или диагнозы». Конкретика болезни — в протоколе/движке и при желании в аннотации на узкой протокольной карте, не в пути ведения.

**BPMN не чек-лист** (дозы, полный список анализов). На диаграмме — фаза, шаг, развилка.

**Аудитория подписей — врачи.** Только русский клинический язык.  
Запрещено в `name`: имена файлов, коды движка, ATC «как есть», жаргон разработки.

Связь с реестром: стабильный XML `id` = `bpmn_task_id` в YAML.  
Узкие протокольные BPMN (`cap-*`, `ida-*`) — вспомогательные, не главная демо-схема.

## 1. Канонические файлы

- **`care_outpatient`** → `docs/bpmn/care-outpatient-mature.bpmn` — **один визит** (без петель)
- **`care_outpatient_control`** → `docs/bpmn/care-outpatient-control-mature.bpmn` — контроль; исходы — концы
- `cap_inpatient` → `docs/bpmn/cap-inpatient-mature.bpmn` — стационар (пока; обобщение отдельно)
- `cap_outpatient` / `ida_outpatient` → **не путь ведения**: узкие протокольные карты (вторично). Для врачей не открывать как «процесс»

**Не рисовать на одном холсте** петли «коррекция» и «ещё визит» через весь процесс — это и есть паутина.  
Повторное обращение = снова старт визита. Коррекция / ещё визит = конец контроля → новый визит.

Обзор — `PROCESSES_BPMN.md`.  
На диаграмме для врачей — **только клинические** аннотации. Не писать: имена файлов, id процессов, «версия», «двойной клик», «подпроцесс», handoff.

## 1.1. Верхний уровень = подпроцессы

Как в зрелых процессах Alumineu (order fulfillment):

- на **корневой** диаграмме только: старт → **подпроцессы-фазы** → шлюзы между фазами → концы;
- шаги и внутренние развилки — **внутри** подпроцесса (отдельный вид при двойном клике);
- длинные петли на корневой диаграмме **не рисуем** — выносим в отдельный процесс или заканчиваем концом с handoff;
- без дорожек (см. §2).

## 2. Без дорожек (lanes)

Swimlanes на mature BPMN **не рисуем**.  
Роль исполнителя (`lane` в YAML) — метаданные шага, не полосы на картинке.

## 2.1. Layout (читаемость)

Единая сетка для всех mature BPMN:

| Параметр | Значение |
|----------|----------|
| Ось happy path (центр потока) | `y = 200` |
| Задача на оси | высота 80, центр на `y=200` |
| Коридор «нет» / вторичная ветка | сразу **под** осью, зазор ≈ 24px |
| Подпись `да`/`нет` | рядом со своей стрелкой, не в пустоте между рядами |

- Маркер default (косая черта на стрелке) на mature-схемах **не ставим**: ветки уже подписаны, черта выглядит как поломка потока.
- В задачу/подпроцесс — **один** входящий поток. Несколько путей сходятся в пустой XOR-merge перед блоком.
- Happy path — **одна линия слева → направо**. Не разворачивать второй ряд справа налево.
- Ветки «да» у шлюза — **на основной линии** (предпочтительно) или коротко **вверх** (стационар / ошибка).
- Ветки «нет» — **под** happy path или в сторону; без «улетевших» задач.
- Канон у шлюза госпитализации:
  - «да» — **вверх** к «В стационар»; подпись `да` — **справа** от вертикали;
  - «нет» — **вправо** (запас ≥ 100px до блока); подпись `нет` — **над** стрелкой;
  - петля — в **низ** ромба;
  - вопрос шлюза — **слева-снизу** от ромба (не сверху на «да», не справа на «нет»/таск).
- Любая подпись не должна пересекать линию потока и другую подпись.
- Аннотации КП — слева-сверху, короткая ассоциация; не через поток.
- Boundary на подпроцессе — **не по центру низа** (там `[+]`). Ставить слева/справа на нижней кромке; подпись — **сбоку** от стрелки, не под кружком.

## 3. Язык и стиль подписей

| Где | Правило |
|-----|---------|
| `name` на фигуре | **только русский**, этап бизнеса: «Осмотр», «Антибактериальная терапия» |
| XML `id` | стабильный EN: `Task_PrescribeAbt` — для связи с YAML |
| Аннотация у шлюза / шага | коротко по смыслу для врача; номер КП — только на **узких** протокольных схемах |
| Дозы, списки анализов, поля карты | **не** в `name` |

**Хорошо (ведение):** `Оценить состояние и эффект` · шлюз `Есть улучшение?` · аннотация про сверку с протоколами  
**Плохо:** `Оценить эффект АБТ через 48–72 ч: лихорадка <38…` / отдельная ветка «если пневмония»

Задачи — существительное/краткий глагол этапа, не повелительная инструкция на полэкрана.  
Шлюзы — вопрос с `?`. Ветки — `да` / `нет`.

## 4. Именование id (XML)

- `Start_…`, `End_…`, `Task_…`, `Gateway_…` — не менять без нужды (`bpmn_task_id` в YAML).
- `SubProcess_…`, `Event_…` — по необходимости.

## 5. Gateways — точки сверки с протоколом

| id | Аннотация / смысл |
|----|-------------------|
| `Gateway_Hospitalization` | КП №768, п.26 → стационар (после первичного приёма) |
| `Gateway_NoEffectNext` | КП №768, п.15 → нет эффекта: стационар или сменить лечение |
| `Gateway_Icu` | КП №768, п.27 → ОРИТ |
| `Gateway_AbtEffect` / `_in` | КП №768, п.15 / п.30 |
| `Gateway_Discharge` | КП №768, п.49 |
| `Gateway_Goal` | достижение цели лечения |

Критерии «да/нет» подробно — в YAML и в `protocol_cap`, не на стрелках.

## 6. Связь с YAML

- `step.bpmn_task_id` = XML `id` (или `null`).
- Детали протокола, SQL-проверки, сигналы SLA — только YAML.
- Приоритет при конфликте: **YAML + КП №768** → потом BPMN.

## 7. Не плодить статусы

Тяжесть, эффект, готовность к выписке — **вычисляются**. В BPMN это gateway; в данных — `observation` / `clinical_flag`.

## 8. Таймеры и handoff

SLA (48–72 ч, 4–6 нед) — в YAML `signals` / `sla_targets`, не в длинном `name` задачи.  
Handoff амбулаторный → стационар: `End_Hospitalized` + `process_handoffs`.

## 9. Инструменты

Camunda Modeler / bpmn.io. Layout чужой диаграммы не трогать без запроса.

Автопроверка канона: `python3 tools/test_bpmn_layout.py` (обязательна после правок `docs/bpmn/*mature*.bpmn`).
