# BPMN Practices — практики моделирования для clinic-os

Канон рисования BPMN для процессов внебольничной пневмонии.

## 0. Главный принцип: процесс ≠ инструкция

| Слой | Что это | Где живёт |
|------|---------|-----------|
| **Бизнес-процесс** | Этапы ведения эпизода и решения («что происходит») | BPMN `name` на фигурах |
| **Протокол / регламент** | Критерии, дозы, списки исследований, пункты КП («как решать правильно») | КП №768 + `process_registry.yaml` (`intent_ru`, `legal_basis_ru`) + код `protocol_cap` |
| **Инструкция UI** | Какие поля заполнить в карте | экран приложения, не BPMN |

**BPMN не должен превращаться в чек-лист** («измерить t, SpO2, ЧД…», «цефтриаксон 1–2 г», «ОАК+СРБ+ПКТ+ОАМ»).  
Такие детали — в YAML и в протоколе. На диаграмме остаётся **этап и развилка**.

**BPMN должен позволять сверяться с протоколом:**
- каждый ключевой шаг/шлюз имеет стабильный XML `id` = `bpmn_task_id` в YAML;
- у шага в YAML есть `intent_ru` и ссылка на пункт КП;
- на диаграмме у развилок — короткая аннотация `КП №768, п.…` (не простыня текста).

Цепочка сверки:

```
картинка BPMN (этап)
    ↔  process_registry.yaml (intent + п. протокола)
    ↔  КП МЗ РБ №768 / код protocol_cap
```

При расхождении приоритет у **YAML + протокола**; BPMN подчищаем под них.

## 1. Один процесс — один канонический BPMN

- `cap_outpatient` → `docs/bpmn/cap-outpatient-mature.bpmn`
- `cap_inpatient` → `docs/bpmn/cap-inpatient-mature.bpmn`

Обзор для нетехнической аудитории — Mermaid в `PROCESSES_BPMN.md`.  
На диаграмме: `TextAnnotation` с версией даты.

## 2. Без дорожек (lanes)

Swimlanes на mature BPMN **не рисуем**.  
Роль исполнителя (`lane` в YAML) — метаданные шага, не полосы на картинке.

## 2.1. Layout (читаемость)

- Happy path — **одна линия слева → направо**. Не разворачивать второй ряд справа налево.
- Ветки «да» у шлюза — по основной линии или **вверх** (handoff / конец).
- Петли «нет» — **под** happy path, каждая на своём горизонтальном коридоре (разный `y`), без пересечения стрелок.
- Аннотации `КП №768, п.…` — над шлюзом, не на линии потока.

## 3. Язык и стиль подписей

| Где | Правило |
|-----|---------|
| `name` на фигуре | **только русский**, этап бизнеса: «Осмотр», «Антибактериальная терапия» |
| XML `id` | стабильный EN: `Task_PrescribeAbt` — для связи с YAML |
| Аннотация у шлюза | коротко: `КП №768, п.26` |
| Дозы, списки анализов, поля карты | **не** в `name` |

**Хорошо:** `Оценка эффекта терапии` · шлюз `Есть эффект?` · аннотация `КП №768, п.15`  
**Плохо:** `Оценить эффект АБТ через 48–72 ч: лихорадка <38, снижение СРБ, записать t и SpO2`

Задачи — существительное/краткий глагол этапа, не повелительная инструкция на полэкрана.  
Шлюзы — вопрос с `?`. Ветки — `да` / `нет`.

## 4. Именование id (XML)

- `Start_…`, `End_…`, `Task_…`, `Gateway_…` — не менять без нужды (`bpmn_task_id` в YAML).
- `SubProcess_…`, `Event_…` — по необходимости.

## 5. Gateways — точки сверки с протоколом

| id | Аннотация / смысл |
|----|-------------------|
| `Gateway_Hospitalization` | КП №768, п.26 → стационар |
| `Gateway_Icu` | КП №768, п.27 → ОРИТ |
| `Gateway_AbtEffect` / `_in` | КП №768, п.15 / п.30 |
| `Gateway_Discharge` | КП №768, п.49 |
| `Gateway_Goal` | достижение цели лечения |

Критерии «да/нет» подробно — в YAML и в `protocol_cap`, не на стрелках.

## 6. Связь с YAML

- `step.bpmn_task_id` = XML `id` (или `null`).
- Детали протокола, SQL-проверки, сигналы SLA — только YAML.
- Приоритет при конфликте: **YAML + КП №768** → потом BPMN.

## 7. Не плодить статусы

Тяжесть, эффект, готовность к выписке — **вычисляются**. В BPMN это gateway; в данных — `observation` / `clinical_flag`.

## 8. Таймеры и handoff

SLA (48–72 ч, 4–6 нед) — в YAML `signals` / `sla_targets`, не в длинном `name` задачи.  
Handoff амбулаторный → стационар: `End_Hospitalized` + `process_handoffs`.

## 9. Инструменты

Camunda Modeler / bpmn.io. Layout чужой диаграммы не трогать без запроса.
