## Зачем продукт (north star)

Демо не про «внести данные о пациенте». Главное:

- **подсказывать** врачу по протоколу лечения;
- **проверять** следование протоколу на каждом действии;
- показывать это **удобно в UI** в момент работы с карточкой.

Сейчас UI + архитектура по этой цели ≈ **3/10**. При любом решении (фича, рефакторинг, приоритет) спрашивать: стало ли демо «подсказка + проверка» сильнее? Если нет — отложить.

**Демо = ссылка в облаке.** Человек открывает URL и кликает. Данные и приложение не на ноутбуке. Стек демо: **Render (free) + Supabase Postgres (free)**. Локальный SQLite — только разработка. Не выбирать решения, которые ломают «скинул ссылку → работает».

Контекст протокола: взрослые, КП МЗ РБ №768 (ВП); выбор АБТ — YAML-правила, не `drug_catalog`.

**Пересмотр архитектуры:** можно и нужно усиливать слой «подсказка + проверка» и UX демо. Полный переезд на другой фронт/бэкенд — только если это прямо поднимает демо по ссылке; иначе остаёмся на Flask SSR + облачная БД.

### Как работают подсказки и проверка (сверка)

Система не «угадывает». На каждом шаге:

```
Факты пациента (БД, коды словаря)
        ↓
Ожидание по протоколу (YAML-правила + пороги КП №768)
        ↓
Сравнение → зазоры (нет / не то / дальше сделать)
        ↓
UI врачу: понятный текст + что сделать
```

| Момент | Что делает система |
|---|---|
| **До / в момент действия** | Подсказка: «сейчас ожидается …»; при назначении — сверка препарата/маршрута/дозы (soft warn или hard-stop) |
| **После данных на карте** | Полная проверка эпизода: исследования, тяжесть, госпитализация, АБТ, контроль 48–72 ч |

Сверяется не «текст с текстом», а **код с кодом / число с порогом**:
- факт: ATC назначенного, LOINC SpO2=88, флаг `abt_3mo`, класс encounter;
- ожидание: ATC из `cap_abt_rules.yaml`, SpO2≥…, обязательные CBC/CRP, маршрут oral/iv;
- зазор: нет факта, факт ≠ ожидание, или нужен следующий шаг.

Два слоя ответа врачу (в UI без технических кодов):
1. **Подсказка** — что сделать дальше по протоколу.
2. **Проверка** — что уже сделано не так или не сделано.

Движок сверки: `protocol_cap.evaluate_cap` (+ `protocol_rules` для АБТ). CDS / карточка только **показывают** вердикт, логику не дублируют.

### Свободный текст vs справочник vs выбор протокола

Опыт лучших CDS (SNOMED/AHRQ eRecommendations, CPG-on-FHIR, CDS Hooks):

| Тип данных | Как вводить | Зачем |
|---|---|---|
| Жалобы, анамнез «своими словами», уточнения | **Свободный текст** (narrative) | Для врача и чтения; **не** триггер протокола и не объект жёсткой сверки |
| Диагноз, препарат, показатель осмотра, услуга, флаг риска, аллергия | **Только справочник** (МКБ / ATC / LOINC / флаги) | Статистика + сверка с протоколом |
| Единицы, пороги, допустимые маршруты | **Из словаря**, не с клавиатуры | Уже следуют из выбранного кода |

**Выбор протокола** (как в зрелых системах): не из текста жалоб, а по **кодированному диагнозу** (или явному выбору врача).

```
Жалобы/осмотр/анамнез (текст + коды измерений)
        ↓ помогают врачу
Диагноз МКБ из справочника (врач ставит)
        ↓ inclusion-набор кодов
Протокол (напр. cap_adult_768) → подсказки и проверки
```

Паттерн: у каждого протокола — список кодов МКБ (как сейчас `PNEUMONIA_CODES` → ВП №768).  
При 2+ протоколах — таблица/YAML `protocol_registry`: `protocol_id → icd_codes[]` (+ при необходимости ручной выбор, если коды пересекаются).

**Не делать для демо:** NLP по свободному тексту «угадай протокол» — ненадёжно и не нужно.  
**Не путать:** «данные для диагноза» (осмотр) ≠ «триггер протокола» (код диагноза). Осмотр обязателен для качества записи; протокол включается после МКБ из набора.

Сейчас в коде: `has_pneumonia` / `PNEUMONIA_CODES` → `evaluate_cap`. Это правильная ось; дальше — явный реестр протоколов и UI «диагноз → активный протокол» языком врача.

### Цепочка: этап → терминология → хранение → UI → проверка

Для каждого шага процесса (осмотр, обследования, диагноз, назначение АБТ, контроль…):

1. **Что врач вносит/выбирает** на этом этапе (результаты, флаги, препарат + доза + кратность + маршрут + длительность…).
2. **Терминология** — только из единого словаря (`terminology.py` + связанные справочники: МКБ, LOINC, ATC, флаги, услуги). Свободный текст не заменяет код. Словари сверять с протоколом — это критично для проверок.
3. **Хранение в БД** — форма, удобная для `protocol_cap` / правил (код + значение + дата/связь с encounter; у лекарства — ATC, route, dose, frequency, period_start/end). Не «строка как получилось».
4. **UI** — лучший способ ввода именно для этого элемента; связанные поля связаны (выбрал препарат → подставились допустимые маршруты/доза/кратность из каталога; выбрал показатель → только число).
5. **Проверка** — движок читает те же коды/поля и сравнивает с протоколом (YAML-правила + пороги из словаря).

Без единого словаря и продуманного хранения удобный UI бесполезен для демо «проверка протокола».

### UI (clinic-ui и все, кто трогает templates)

- Мало вложенности и кликов; информация необходимая и достаточная; чистая группировка по **этапу ведения**, не по таблицам БД.
- Ввод: лучший привычный способ для типа данных, не «первый input».
- На экране — язык врача. Без сырых кодов, ATC/LOINC без подписи, имён gap'ов, JSON, отладки.
- Единицу/размерность **не спрашивать**, если показатель уже выбран (SpO2 → только число; система знает `%` и пороги). То же для остальных витальных/лаб.
- Назначение препарата: выбор из словаря + все нужные параметры (доза, регулярность/кратность, маршрут, сроки) — связанные, не разрозненные случайные поля.
- Подсказка и проверка протокола — на виду, не внизу среди форм.
- Размеры/отступы кнопок — только классами из `static/clinic.css` (`.btn`/`.btn-small`/`.action-btn`), никогда `style="height:…/font-size:…"` в шаблоне — иначе кнопки на разных страницах снова разъезжаются по размеру.
- Текст значения атрибута (`.attr-value`) — фрагмент данных, не предложение: без точки в конце, несколько фактов через « · », не через запятую. Правило и примеры: `docs/ui/STYLE_GUIDE.md` §4.5. Касается и текста, который для `.attr-value` готовит протокол/сервис в `.py` (цели лечения, описания), а не только вёрстки.
- Новая страница/форма с `<form method="POST">` подключает `{% include "_double_submit_guard.html" %}` перед `</body>` — не писать защиту от повторной отправки заново, копипастом.
- Список, который растёт годами наблюдения (диагнозы, приёмы — у сущности есть статус активна/закрыта) — активное полной карточкой, закрытое/разрешённое сворачивать в `history-fold` компактной строкой (`.visit-row`), не копить одинаковыми крупными карточками. Правило и таблица: `docs/ui/STYLE_GUIDE.md` §4.7. Данные конкретной записи (цель, вердикт) фильтровать по id этой записи, не показывать список пациента целиком под каждой карточкой.

## Гейты перед сдачей (обязательно, не выборочно)

Три быстрых прогона без БД/сервера или с временной SQLite — не пропускать ни один, даже если задача точечная:

| Гейт | Что проверяет | Когда обязателен |
|---|---|---|
| `python3 tools/scenarios.py` | Протокол/правила (28 сценариев) | тронули protocol_*.py, rules_engine.py, *_rules.yaml |
| `python3 tools/style_gate.py` | Текст-значения без точки/запятой, кнопки без inline-размеров, статусы без сырого enum, формы под double-submit-guard | тронули templates/**, care_plan_service.py, cds_service.py, любой .py с `description=` |
| `python3 tools/quality_gate.py` | ClinicalVerdict без техкодов в UI, структура #now-action | тронули app.py/protocol_verdict.py/templates/patient.html |
| `python3 tools/test_bpmn_layout.py` | Mature BPMN: один вход в task, рёбра прикреплены, нет default/, нет lanes, boundary не на `[+]` | тронули `docs/bpmn/*mature*.bpmn` или `BPMN_PRACTICES.md` |

Если задача добавляет **новый протокол** (по образцу ВП/ЖДА) — все три гейта обязательны сразу, плюс `python3 tools/doctor_gate.py`. Стиль текста цели/подсказки для нового протокола не полагаться на память — прогнать `style_gate.py`, он поймает разъезд с существующими протоколами автоматически.

## Владение файлами

### clinic-architect
- `AGENTS.md`, `docs/architecture.md`, `docs/concepts.md`
- решает пересечения; правит общие файлы при интеграции
- **не** параллелит сам с воркерами в одном working tree

### clinic-protocol
**Можно:**
- `protocol_cap.py`, `protocol_rules.py`, `rules_engine.py`
- `docs/protocols/**` (в т.ч. `cap_abt_rules.yaml`)
- `cds_service.py`, `care_plan_service.py`, `drug_service.py`
- `terminology.py` (коды, флаги, `ADULT_DOSES` — согласовать с data/UI при смене доз)

**Нельзя:** `templates/**`, `tools/e2e_test.py`, `tools/scenarios.py` (кроме правок ожиданий по согласованию с qa)

### clinic-ui
**Можно:**
- `templates/**`
- узкие правки `app.py` (роуты/контекст шаблонов под UI)
- `static/**` если появится

**Нельзя:** `protocol_*.py`, `rules_engine.py`, `docs/protocols/**`, схема БД

### clinic-qa
**Можно:**
- `tools/scenarios.py`, `tools/e2e_test.py`, прочие `tools/test_*.py`
- при необходимости — только ожидания/фикстуры под уже существующее поведение

**Нельзя:** менять прод-логику «чтобы тест прошёл» без эскалации архитектору

### Общие файлы (только architect или по явному разрешению в ТЗ)
`app.py`, `db.py`, `fhir_store.py`, `schema.sql`, `_seed_data.py`, `tools/seed_*.py`

Выбор АБТ — SSOT в `docs/protocols/cap_abt_rules.yaml` (+ `protocol_rules.py`).  
`drug_catalog` — справочник доз/названий для формы, не дерево решений.

## Параллельная работа

1. Один агент = одна git-ветка (лучше отдельный worktree).
2. Ветка: `agent/<имя>/<краткий-таск>`, например `agent/clinic-ui/patient-hint`.
3. В промпте воркеру всегда: список **можно / нельзя**, критерий готовности, «не коммить без спроса».
4. Одновременно: максимум protocol + ui **или** ui + qa, если файлы не пересекаются.
5. Merge по одному: сначала protocol → ui → qa (или как скажет architect).
