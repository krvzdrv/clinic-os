## Что уже сделано

Рабочее Flask-приложение с 4 слоями архитектуры:

```
clinic.db (SQLite, один файл)           ← бэкап = копия файла
  ↑
fhir_store.py (Слой 0: данные)          ← FHIR-подобная модель, 10 тестовых пациентов
  ↑
rules_engine.py (Слой 3: 6 правил)     ← CQL-like, single source of truth
  ↑
cds_service.py (Слой 5: CDS Hooks)     ← карточки info / suggestion / hard-stop
  ↑
app.py (Flask: роуты + UI)             ← один файл, запускается одной командой
```

**6 правил реализованы:**
1. `has_hypertension()` — есть ли активная гипертония (I10)
2. `last_bp()` — последнее измерение АД
3. `uncontrolled_bp()` — АД не контролируется (> 140/90)
4. `bp_overdue()` — передержка наблюдения (нет измерения > 90 дней)
5. `has_diabetes()` — ко-морбидность (E10–E14)
6. `dual_ace_therapy()` — дублирование ингибиторов АПФ

**Single source of truth:** `uncontrolled_bp()` используется и для подсказки
врачу (через `cds_service`), и для метрики качества на дашборде
(через `quality_measure_controlled()`). Один код — два применения.

**UI:**
- `/` — дашборд (метрика качества + список пациентов с флагами)
- `/patient/<id>` — карта пациента с CDS-карточками
- `/patient/<id>/bp` — форма записи нового измерения АД
- `/export` — экспорт в CSV для отчётов
- `/cds-services/patient-view` и `/cds-services/order-sign` — CDS Hooks API (JSON)

**Запуск локально:**
```bash
cd ~/Projects/hypertension-cds-demo
pip3 install -r requirements.txt
python3 app.py
# → http://127.0.0.1:5566
```

## Ключевые архитектурные решения (и почему)

| Решили | Вместо | Почему |
|---|---|---|
| SQLite (файл) | HAPI FHIR + PostgreSQL | один файл, бэкап = копия, без Java, поддерживаемо одним человеком |
| Python-функции | CQL Engine (cql-execution) | читается как текст, без Java, без отдельного сервиса |
| State machine в таблице | CPG-on-FHIR (PlanDefinition) | 6 этапов достаточно для одного протокола, CPG — при росте |
| Монолит (Flask) | микросервисы | один URL, один процесс, ноль сложности для маленькой клиники |
| Без Camunda/BPMN | Camunda | BPMN — для орг-процессов (согласования, SLA). У нас их нет. Встаёт позже без переписывания правил |
| Flask-шаблоны (HTML/CSS) | React + SPA | без сборки, без npm, поддерживаемо |

**Что НЕ пожертвовали (принципы сохранены):**
- Single source of truth
- FHIR-подобная модель (миграция на настоящий FHIR без боли)
- CDS Hooks концепция (карточки в момент работы врача)
- Слои разделены (данные / правила / сервис / UI)
- Alert fatigue управление (мало карточек, только релевантные)

## Что дальше (возможные направления)

1. **Деплой на PythonAnywhere** — залить код на GitHub, создать веб-приложение,
   получить рабочую ссылку `https://имя.pythonanywhere.com`. Инструкция в
   `docs/deployment.md`.

2. **Расширение протоколов** — добавить диабет (СД 2 типа) как второй протокол:
   новые правила в `rules_engine.py`, новые карточки в `cds_service.py`,
   отдельная метрика на дашборде.

3. **Аутентификация врача** — простой логин (Flask-Login), чтобы разные врачи
   видели своих пациентов.

4. **История измерений** — сейчас хранится только последнее АД. Добавить
   график динамики АД во времени (Chart.js, без бэкенда).

5. **Интеграция с существующей МИС** — импорт пациентов из CSV/Excel,
   который клиника уже ведёт.

6. **Реальные данные** — заменить тестовых пациентов на реальных
   (форма добавления пациента, импорт).
